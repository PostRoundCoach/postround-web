## Task: Build the Public Creator Slug Page System

Build the V1 public creator-page system for Post Round on the **web project only**.

### Important scope

This is a WEB-ONLY feature.

Do NOT modify:

* the Expo/mobile app
* iOS/Android code
* EAS configuration
* mobile navigation
* mobile APIs
* Creator Dashboard functionality

The purpose of this task is to create a reusable public creator-page template that is populated from the existing Supabase creator data.

---

# Core concept

We want ONE reusable public page template.

For example:

`/creators/in2golf`

`/creators/brothers-golf`

`/creators/japes-golf`

All of these URLs must render the same page/template, populated with the corresponding creator's database record.

Do NOT create individual hardcoded pages for individual creators.

The architecture should be:

`URL slug → creator_profiles record → reusable creator page template`

---

# Existing database schema

We already have:

### creator_profiles

Current fields include:

* `id`
* `user_id`
* `display_name`
* `bio`
* `avatar_url`
* `status`
* `created_at`
* `updated_at`

Example existing record:

```text
id: 0d3c3e3e-c040-456a-9aec-a3083fccbaed
user_id: 0d3c3e3e-c040-456a-9aec-a3083fccbaed
display_name: In2Golf
bio: Join us for some winter golf!
avatar_url: null
status: active
```

### Creator_social_accounts

Already exists with:

* `creator_id`
* `platform`
* `handle`
* `profile_url`
* `created_at`
* `updated_at`

Use this existing table for public creator social links.

Do NOT create a duplicate social-account table.

---

# Database changes

First inspect the existing schema and migrations.

Add a `slug` field to `creator_profiles` if one does not already exist.

Requirements:

* `slug` should be unique
* lowercase
* URL-safe
* suitable for use in a URL
* stable
* should not be automatically changed once assigned unless explicitly updated
* existing creator records should remain valid

Add an appropriate UNIQUE constraint/index on `creator_profiles.slug`.

Use the existing `status` field for determining whether a creator is active/public rather than creating a redundant `is_active` field unless there is a compelling reason in the existing architecture.

Do NOT create unnecessary new creator tables.

### Slug examples

```text
In2Golf → in2golf
Brother's Golf → brothers-golf
Japes Golf → japes-golf
Bogey Book Golf → bogey-book-golf
```

The exact slug should be stored in the database rather than generated dynamically on every request.

Do not overwrite or regenerate existing slugs automatically.

---

# Public creator route

Create the dynamic public route:

`/creators/[slug]`

For example:

`https://postroundcoach.com/creators/in2golf`

The route should:

1. Receive the slug from the URL.
2. Query `creator_profiles` for that slug.
3. Require the creator to have `status = 'active'`.
4. Load the creator's public social accounts from `Creator_social_accounts`.
5. Render the reusable creator-page template.
6. Return a proper 404 if the slug does not exist or the creator is not active.

There should be NO hardcoded creator-specific routing.

---

Create/use a deliberate public creator data shape containing only fields appropriate for public display.

### Social accounts

* story candidates

The public page should have no dependency on private Creator Dashboard data.

# Template architecture

The implementation must make it obvious that there is one reusable template.

Conceptually:

```text
/creators/[slug]
       ↓
loadPublicCreator(slug)
       ↓
PublicCreatorPage
       ↓
creator-specific data
```

Do NOT create:

```text
/pages/in2golf
/pages/japes-golf
/pages/brothers-golf
```

or any equivalent hardcoded creator pages.

Adding a new creator later should require only:

1. adding/populating the creator database record
2. assigning a unique slug
3. optionally adding social accounts

The page itself should require NO code change.
