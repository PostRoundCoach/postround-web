# Investigate and Troubleshoot Post Round Creator Signup → Android App Handoff

## Objective

Investigate and resolve the Android app-launch handoff from the Post Round creator signup confirmation page.

**Project scope: Post Round web project only.**

Production creator signup and attribution have now been tested successfully. A production test account was created through a creator referral link, its favourite creator attribution was verified directly in the production database, and the user can successfully open the installed Android app and log in with that account.

However, when the user taps **Open Post Round** on the web signup confirmation page, the browser navigates to a bare `golf-coach://` URI and the expected app handoff does not complete correctly.

We need to establish exactly why this happens and fix the web launch mechanism without disturbing the working production signup, attribution, or authentication flows.

## Phase 2 — Determine the failure mechanism

Investigate these possibilities individually and distinguish verified findings from hypotheses:

1. The click handler constructs `golf-coach://` without a valid path or destination.
2. The browser blocks, ignores, or handles the custom scheme differently depending on browser and Android version.
3. The implementation attempts to launch the app through an invalid or incomplete Android intent URI.
4. The intended destination is lost during routing, URL encoding, or redirect handling.
5. The web page assumes that a custom scheme alone guarantees app launch.
6. The launch attempt fails silently because there is no valid fallback or failure handling.
7. The implementation expects an existing app session to be transferred from the browser when no such mechanism exists.
8. The launch succeeds but does not navigate to the intended in-app screen.

Determine which failure is actually supported by the evidence.

Keep these behaviors separate in the investigation:

- **App launch:** Does tapping the button open the installed app?
- **Destination routing:** Does the app open the intended screen or destination?
- **Authentication:** Does the user remain authenticated, or need to log in?
- **Session handoff:** Is any authenticated web session explicitly and securely transferred to the app?

Do not assume that success in one category proves success in the others.

## Phase 3 — Evaluate the safest web-only fix

After documenting the root cause, propose the smallest appropriate change.

Evaluate the following options against the existing architecture:

### Option A: Correct the existing custom-scheme launch

If the application already supports the intended deep-link destination, correct the URL construction and button handler. Preserve the established scheme and routing conventions wherever possible.

### Option B: Android intent URI with fallback

If justified by the current implementation, evaluate an Android-compatible intent URI that targets the verified package and includes an appropriate HTTPS fallback.

Do not invent a deep-link path or assume that the app supports a particular route. Verify the actual registered handlers and supported destinations first.

### Option C: Verified HTTPS Android App Links

Evaluate HTTPS App Links only if the existing app configuration and domain setup support them or if the investigation demonstrates why this is the appropriate longer-term fix.

Before recommending this option, identify the exact prerequisites, including Android intent filters and domain verification through `assetlinks.json`. These may require a future Android release or domain configuration change, so do not silently introduce them into this web-only task.

### Fallback behavior

The user must not be left on a blank page or a bare custom-scheme URI if the launch attempt fails.

Where appropriate, provide a reliable fallback to the correct Google Play listing or an explanatory web page. Verify the real Play Store URL from the project's existing configuration before using it.

Do not promise automatic authentication or session transfer unless an existing, verified, secure implementation supports it.
