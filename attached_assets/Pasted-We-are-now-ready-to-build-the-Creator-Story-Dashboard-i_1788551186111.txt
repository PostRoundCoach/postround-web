The existing creator/story functionality already exists in the separate app/backend project. Do NOT recreate backend functionality, invent API endpoints, or modify the backend.

## PRODUCT

Post Round Creator Dashboard.

The dashboard is for a creator who has followers using Post Round. Followers can explicitly grant a compelling round story to their selected creator. The creator can review permitted stories and generate social content from them.

The UI should feel like Post Round: confident, editorial, trustworthy, polished. Do not make it look like an admin template.

## EXISTING CONTRACTS

### 1. Active Creator Profiles

There is NO API route.

Use the authenticated Supabase client directly:

```ts
supabase
  .from("creator_profiles")
  .select(`
    id,
    display_name,
    bio,
    avatar_url,
    status,
    created_at,
    updated_at,
    creator_social_accounts(
      id,
      platform,
      handle,
      profile_url
    )
  `)
  .eq("status", "active")
  .order("display_name", { ascending: true })
```

Returned shape:

```ts
{
  id: string;
  display_name: string;
  bio: string | null;
  avatar_url: string | null;
  status: "active";
  created_at: string;
  updated_at: string;
  creator_social_accounts: {
    id: string;
    platform: string;
    handle: string;
    profile_url: string | null;
  }[];
}
```

Do NOT expose or request `user_id`.

### 2. Creator Story Queue

There is NO GET API endpoint.

Use the authenticated Supabase client directly:

```ts
supabase
  .from("story_candidates")
  .select(`
    id,
    story_type,
    headline,
    summary,
    story_data,
    round_id,
    status
  `)
```

RLS provides the authorization boundary.

The existing RLS policy only permits a creator to see stories where:

* the creator owns the creator profile,
* permission_granted = true,
* revoked_at IS NULL.

DO NOT bypass RLS.
DO NOT use service-role credentials.
DO NOT query arbitrary story candidates.

The dashboard should rely on the authenticated user's Supabase session.

### 3. Generate Content

Existing API endpoint:

POST `/api/content/generate`

Headers:

```text
Authorization: Bearer <supabase-access-token>
Content-Type: application/json
```

Request:

```json
{
  "creator_id": "uuid",
  "story_id": "uuid"
}
```

Both fields are required together.

Success:

```json
{
  "ok": true,
  "count": 3
}
```

The generated ContentIdea records are persisted to `content_ideas`.

The creator must:

* own creator_id,
* have an active creator profile,
* have ai_coaching feature access,
* have active permission for story_id,
* have story status of offered or shared.

The web client must not attempt to reproduce these authorization checks. The backend remains authoritative.

Errors include:

* 400 invalid creator/story combination
* 401 authentication failure
* 403 creator authorization failure
* 403 story permission failure
* 403 entitlement failure
* 500 generation failure
* 500 parse failure
* 500 save failure

### 5. Story Dismissal / Revocation

IMPORTANT:

There is currently NO creator-side revocation endpoint.

Do NOT invent one.

The existing:

PATCH `/api/stories/candidates/:id/status`

is follower-side only and can set:

* `kept_private`
* `expired`

A creator cannot use it.

Therefore the dashboard must NOT present a creator "Revoke" action that calls this endpoint.

If dismissal is required by the current UI specification, surface this as an integration limitation rather than implementing an incorrect authorization flow.
