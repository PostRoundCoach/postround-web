## Objective

I have already built a substantial backend analytics and diagnostic system for PostRound Coach, including VAD/capture diagnostics and structured event logging.

I also have a separate Replit web/admin project with an existing admin page that I can currently access via browser using an admin account.

I want to turn the **web/admin project into a centralized Analytics & Diagnostics Command Center** where I can easily understand what is happening inside the application in real-world use.

### VERY IMPORTANT

**Do not replace, duplicate, or redesign existing analytics/diagnostic infrastructure unnecessarily.**

First, inspect the existing codebase, database schema, Supabase tables, Edge Functions, API endpoints, logging systems, diagnostic systems, event structures, and admin functionality.

Identify what already exists and integrate it into the admin interface.

The goal is to create a useful visualization/query layer on top of the existing systems.

# Phase 3 — Create a Unified Admin Analytics Layer

Do not force unrelated systems into a single database table if that would damage the existing architecture.

Instead, create a sensible **analytics/diagnostics abstraction layer in the web project** that can query the existing sources.

The admin UI should make it easy to move from:

**High-level application health → feature → session → event → diagnostic details**

For example:

Dashboard:

> "Something is wrong with Round Buddy."

Click Round Buddy:

> "Most failures are occurring in On Course / noisy environments."

Click environment:

> "Most failures occur when speech is followed by intermittent above-threshold metering."

Click session:

> Show the complete event timeline.

This should feel like an **investigation tool**, not just a collection of charts.

# Phase 12 — Architecture Requirements

Follow these principles:

### 1. Reuse existing infrastructure

Do not create duplicate event tracking.

### 2. Read-only first

The initial analytics/diagnostics interface should primarily be read-only.

Do not allow the admin dashboard to mutate production application data unless there is an existing, clearly justified admin operation.

### 3. Secure it

This is an internal admin interface.

Ensure appropriate authentication/authorization and do not expose sensitive user information unnecessarily.

### 4. Don't move analytics logic into the frontend unnecessarily

The web UI should query appropriate backend/API/database layers rather than embedding business logic everywhere.

### 5. Don't expose secrets

Never expose:

* API keys
* Stripe secrets
* Supabase service-role keys
* OpenAI credentials
* private tokens

### 6. Preserve existing functionality

Do not break the existing admin page or existing analytics infrastructure.
