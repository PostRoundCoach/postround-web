# Implement Web Creator Dashboard Contract

## Objective

Implement the web/API changes identified by the completed **Web Creator Dashboard Contract Audit**.

The audit document is:

`docs/web-creator-dashboard-contract-audit.md`

The canonical app-side scoring contract is:

`docs/rounds-scoring-audit.md`

The existing web dashboard contract is:

`CREATOR_DASHBOARD_ROUND_CONTRACT.md`

The audit was performed before the app-side Rounds Scoring Contract implementation was completed. **Task #954 is now complete.** Therefore, do not blindly reproduce the audit's historical "pending migration" state. Reconcile the web implementation against the **current canonical schema and app-side contract**.

This task is an **implementation task**, not another audit.

# Critical Rules

## 1. `docs/rounds-scoring-audit.md` is the canonical scoring contract

The app-side contract is authoritative for:

* field names
* field meanings
* nullability
* scoring definitions
* overlap semantics
* input methods
* round-level vs hole-level fields

Do not invent alternate definitions on the web side.

## 2. `score_to_par` is now a database-generated column

Task #954 implemented the canonical generated field:

`rounds.score_to_par`

It represents:

`total_score - course_par`

**Do NOT calculate `score_to_par` in the web application.**

The API should SELECT the database-generated value and pass it through to the dashboard.

There must be one canonical calculation: PostgreSQL.

## 3. `course_par` is now canonical

The app-side contract changed the round-level field from:

`rounds.par`

to:

`rounds.course_par`

The coordinated schema migration has been completed by Task #954.

Do not revert the API or web code back to round-level `par`.

Important distinction:

* `rounds.course_par` = course/round-level par
* `holes.par` = individual hole par

The hole-level `par` field is correct and must remain `par`.

## 4. Do NOT involve `player_stories`

This is extremely important.

`player_stories` is a separate player-facing product.

It is NOT a creator-content source.

The creator pipeline remains:

`story_candidates`
→ `story_permissions`
→ `content_ideas`
→ `GET /api/content/ideas`
→ Creator Dashboard

Do not add:

* `player_stories` joins
* `player_stories` fallbacks
* Player Story data to creator approval
* Player Story data to creator content
* Player Story data to `content_ideas`
* Player Story data to the Creator Dashboard

The existing isolation identified by the audit is correct and must remain intact.

## 5. Do not modify unrelated product behavior

This task is specifically about bringing the web Creator Dashboard/API into alignment with the canonical rounds contract.

Do not:

* redesign the dashboard
* change creator permissions
* change story qualification
* change Player Stories
* change AI generation
* change scoring calculations in the app
* change mobile behavior
* reintroduce Voice Recap
* add new product features

Keep the change tightly scoped.

`"scorecard" | "voice_recap" | "guided_ai" | null`

The canonical supported values are:

`"scorecard" | "round_buddy"`

Before changing anything, inspect the **current database schema** and existing application code to determine whether `rounds.input_method` actually exists and is populated.

Then:

* SELECT it in `GET /api/content/ideas`
* expose it to the web
* update the dashboard contract to:

`"scorecard" | "round_buddy" | null`

### If `rounds.input_method` does not exist / is not part of the current canonical schema:

* do NOT create a new database column solely for this web task
* remove it from the dashboard contract rather than documenting a field the API cannot provide

Do not add `"voice_recap"` or `"guided_ai"`.

Do not invent a value.

# D. Update `three_putts` semantics

The dashboard contract must explicitly preserve the canonical null semantics:

* `three_putts = null` means per-hole putting data was unavailable
* `three_putts = 0` means putting data was available and there were zero three-putts
* a positive value means that many three-putts occurred

Do not convert `null` to `0`.

Do not use `|| 0` or equivalent behavior that destroys this distinction.

# H. Creator permission behavior must remain unchanged

1. Require authentication.
2. Resolve the creator from the authenticated bearer token.
3. Require an active `creator_profiles` record.
4. Require valid `story_permissions`.
5. Require `permission_granted = true`.
6. Require `revoked_at IS NULL`.
7. Require the appropriate story candidate status.
