# Task: Ensure Coaching Session VAD Telemetry Is Fully Captured and Visible on the Web Project

The mobile Coaching Session VAD implementation has now been updated to generate structured `COACH_*` telemetry, establish the telemetry context before metering begins, refresh context on audio-route changes, flush telemetry after successful voice-turn submission, and clear stale telemetry on exit/failure paths.

The mobile test suite currently passes:

* 3,162 golf-coach tests
* 724 API-server tests
* 14 new `vadProfileSelector.test.ts` tests

Now focus specifically on the **web/API/database/session-diagnostics side**.

## Primary objective

Ensure that Coaching Session VAD telemetry generated by the mobile application makes it completely through the web system:

```text
Mobile Coaching Session
        ↓
vadTelemetry queue
        ↓
POST /api/coaching/vad-telemetry
        ↓
API-server route
        ↓
database persistence
        ↓
session diagnostics query
        ↓
Web Session Diagnostics UI
```

The acceptance criterion is:

> After completing a real Coaching Session, the web project's Session Diagnostics page must show the persisted `COACH_*` VAD events for that session.

Do not modify the mobile VAD algorithm as part of this task unless absolutely necessary to resolve an API contract mismatch.

# 8. Pay particular attention to audioOutputRoute

The mobile implementation has now been updated so that `audioOutputRoute` should be populated from the runtime audio environment.

Make sure the web/API layer does not discard it.

This field is particularly important for diagnosing the current problem:

```text
Speakerphone → works
Hearing-aid Bluetooth → works
Car Bluetooth / Android Auto → problematic
```

The diagnostics page needs to show enough information to distinguish those environments.

If the API schema currently strips `audioOutputRoute`, fix that.

# 10. Verify authentication

The mobile telemetry request uses the session's authentication headers.

Confirm that `/api/coaching/vad-telemetry`:

* authenticates the request correctly
* associates the telemetry with the authenticated user
* does not accidentally reject Coaching telemetry
* does not allow telemetry to be written against another user's session/round

Do not weaken authentication or authorization simply to make telemetry work.

---

# 11. Verify failure behavior

Telemetry must remain non-critical.

If:

```text
POST /api/coaching/vad-telemetry
```

fails:

* Coaching Session must not fail.
* The coaching response must not be blocked.
* The user must still be able to complete the turn.
* The API should return an appropriate failure response.
* Existing client-side queue/retry behavior should be allowed to handle transient failures.

Do not introduce synchronous dependencies between telemetry persistence and the actual Coaching Session response.

## Definition of Done

This task is complete only when all of the following are true:

* `COACH_*` telemetry is accepted by the API.
* Coaching telemetry is authenticated.
* Coaching telemetry is associated with the correct session/clientRoundId.
* `holeNumber = null` is supported for Coaching Sessions.
* All required payload fields survive API validation.
* Events are persisted in the existing telemetry storage.
* Session Diagnostics retrieves Coaching telemetry.
* Session Diagnostics displays Coaching telemetry.
* `audioInputRoute` and `audioOutputRoute` are visible.
* `vadProfile` is visible.
* `COACH_METER` aggregated statistics are visible.
* Anomalies are visible.
* Existing Round Buddy telemetry continues to work unchanged.
* Telemetry failure cannot break a Coaching Session.
* All existing API/web tests pass.
* New end-to-end Coaching telemetry tests pass.
* A real Coaching Session can be verified in the web diagnostics page.

### Most important acceptance test

Do not declare this complete based solely on unit tests.

The final proof is:

> **Complete one real Coaching Session on the Android device, then open that session in the web project's Session Diagnostics and confirm the persisted `COACH_*` VAD timeline is present.**

Once that works, we will finally have the instrumentation necessary to diagnose the car Bluetooth problem from an actual highway session rather than guessing from client-side logs.
