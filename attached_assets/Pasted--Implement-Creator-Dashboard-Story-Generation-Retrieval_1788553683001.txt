# Authoritative API contract

The web dashboard already has access to the authenticated Supabase session/token.

Use the existing API base configuration:

`NEXT_PUBLIC_POSTROUND_API_BASE_URL`

The API calls must include the Supabase access token as:

`Authorization: Bearer <access_token>`

## 1. Generate creator content

Existing endpoint:

`POST /api/content/generate`

Request body:

```json
{
  "creator_id": "<creator profile UUID>",
  "story_id": "<story candidate UUID>"
}
```

Both IDs are required.

Successful response:

```json
{
  "ok": true,
  "count": 3
}
```

The generated ideas are persisted by the backend. The POST response does NOT contain the generated ideas themselves.

## 2. Retrieve generated ideas

New authoritative endpoint from Task #787:

`GET /api/content/ideas?story_id=<story UUID>`

The backend derives the authenticated creator from the Supabase user and verifies that the creator has permission to access the requested story.

Successful response:

```json
{
  "ok": true,
  "ideas": [
    {
      "id": "uuid",
      "story_id": "uuid",
      "category": "Practice Tip",
      "title": "Example title",
      "hook": "Example hook",
      "script": "Example script",
      "created_at": "2026-09-04T..."
    }
  ]
}
```

An authorized story with no ideas returns:

```json
{
  "ok": true,
  "ideas": []
}
```

Do not expose or depend on `stats_used` or internal `status` fields.

# Required user flow

The Creator Dashboard flow should be:

**Creator opens dashboard → sees permitted story → clicks Generate Content → POST `/api/content/generate` → backend generates/persists ideas → GET `/api/content/ideas?story_id=...` → render the real generated ideas.**

Do not generate automatically on page load.

Do not generate automatically on rerender.

Generation must happen only from the existing explicit user action.

---

# Generation state

While POST `/api/content/generate` is running:

* show a clear loading state on that story
* prevent accidental duplicate generation requests
* keep the story visible
* do not affect other stories

If generation succeeds:

1. use the returned `count` only as confirmation that generation succeeded
2. immediately call `GET /api/content/ideas?story_id=...`
3. render the returned ideas

Do NOT fabricate ideas from the POST response.

---

# Retrieval state

Treat generation and retrieval as two separate operations.

### Generation failure

If POST fails:

* show a generic user-friendly error
* preserve the story
* allow the user to retry generation
* do not call GET if generation did not succeed

### Retrieval failure

If POST succeeds but GET fails:

* do NOT call POST again automatically
* preserve the story
* show an error indicating that the generated content could not be loaded
* provide a **retry retrieval** action
* retrying retrieval must call only GET

This distinction is important because generation may already have succeeded on the backend.

### Empty result

If GET succeeds with:

```json
{ "ok": true, "ideas": [] }
```

show a clean empty state rather than fabricated content or an error.
