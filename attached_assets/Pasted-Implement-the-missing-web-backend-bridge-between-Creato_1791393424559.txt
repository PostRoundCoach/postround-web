Implement the missing web/backend bridge between Creator referral attribution and the player's `profiles.favorite_creator_id`.

## CONTEXT

I just completed a real smoke test of the Creator referral signup flow.

Observed database state for the newly created referred player:

### Player profile

`profiles` contains the new player, but:

`favorite_creator_id = NULL`

### Referral attribution

The same user has a valid `creator_attributions` record containing:

* `user_id` = the new player
* `creator_id` = the correct referred Creator
* `attribution_method` = `web_referral`
* `attribution_source` = `creator_referral`

The referral event and attribution are therefore working correctly.

The bug is the missing bridge:

```text
creator_attributions.creator_id
            ↓
profiles.favorite_creator_id
```

The native app currently has no Creator to display because the player's profile has no `favorite_creator_id`.

---

# OBJECTIVE

Modify the **web/server-side referred-account completion flow** so that when a new player is successfully attributed to a Creator through the Creator referral flow, the player's:

```text
profiles.favorite_creator_id
```

is populated with:

```text
creator_attributions.creator_id
```

Do this on the backend/web flow, **not in the native mobile app**.

The referral attribution remains the authoritative source for determining which Creator was referred.

---

# REQUIRED BEHAVIOR

## 1. New referred player

When a new player completes a valid Creator referral signup and a corresponding `creator_attributions` record exists:

```text
creator_attributions.user_id = player_id
creator_attributions.creator_id = creator_id
```

then ensure:

```text
profiles.favorite_creator_id = creator_id
```

for that player.

The intended flow is:

```text
Creator referral slug
        ↓
creator_referral_events
        ↓
creator_attributions
        ↓
profiles.favorite_creator_id
        ↓
native app login
        ↓
Creator available as player's favorite
```

---

## 2. NEVER overwrite an existing favorite

This is critical.

If the player already has:

```text
profiles.favorite_creator_id IS NOT NULL
```

do **not** replace it with the referred Creator.

A referral should establish the default Creator for a player who does not already have one.

For example:

```text
favorite_creator_id = NULL
creator_attributions.creator_id = ABC
→ set favorite_creator_id = ABC
```

But:

```text
favorite_creator_id = XYZ
creator_attributions.creator_id = ABC
→ leave favorite_creator_id = XYZ
```

The player's intentional Creator selection must take precedence over referral attribution.

---

# 3. Do not make the mobile app responsible for referral logic

Do NOT implement logic in the native app such as:

> "If favorite_creator_id is NULL, search creator_attributions and populate it."

That is not the desired architecture.

The backend already knows the authoritative relationship.

The native app should simply receive the resulting player profile/state and see:

```text
favorite_creator_id = creator_id
```

Referral/business logic should remain server-side.

# 5. Handle duplicate/repeated referral processing safely

The operation must be idempotent.

If the same referred signup/claim is processed more than once:

* do not create duplicate attribution records
* do not repeatedly modify the player's favorite
* do not overwrite an existing favorite
* do not produce an error simply because `favorite_creator_id` is already populated with the correct Creator

The operation should safely produce the same final state when retried.
