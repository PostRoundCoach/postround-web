# Build a Minimal VAD Diagnostics Dashboard

On the **existing web admin page**, add a new section called:

## VAD Diagnostics

The purpose of this is **testing and troubleshooting**, not building a full analytics platform.

I want a simple way to see what is happening with VAD during real-world testing of Round Buddy and Coaching.

### IMPORTANT

Before coding, inspect the existing backend/database and determine what VAD diagnostic data already exists.

**Reuse the existing telemetry and events. Do not create a new analytics architecture unless something absolutely necessary is missing.**

Also inspect the existing multi-profile VAD implementation and use its canonical profile/environment representation. **Do not hard-code profile names.**

---

## 1. VAD Health Summary

Create a simple summary showing whatever can reliably be calculated from the existing data:

* Total VAD interactions
* Automatic terminations
* Manual terminations
* Premature terminations
* Failed terminations
* VAD anomalies
* Average recording duration
* Average silence duration before automatic termination

Show both counts and percentages where appropriate.

If a metric cannot currently be calculated reliably from existing telemetry, don't invent it. Just omit it or label it as unavailable.

---

## 2. VAD Profile Breakdown

Show VAD performance broken down by the **actual profiles currently used by the application**.

Do not hard-code:

* On Course
* Earbuds
* Speakerphone
* Android Auto
* CarPlay

Those are examples only.

Read the actual profile/environment information from the existing system.

For each profile, show:

| Profile | Sessions | Auto End % | Manual % | Failures | Anomalies |
| ------- | -------: | ---------: | -------: | -------: | --------: |

This is primarily so I can see whether one VAD profile is behaving significantly worse than another.

---

## 3. Recent VAD Sessions

Show a simple list/table of recent Round Buddy and Coaching voice interactions.

Include whatever information already exists, such as:

* Timestamp
* Feature
* VAD profile
* Environment/device context
* Recording duration
* Termination reason
* Automatic vs manual
* Anomaly indicator

Clicking a session should open its detailed diagnostic information.

---

# 4. VAD Event Timeline

This is the **most important part**.

For an individual session, show the existing structured VAD events chronologically.

For example, if these events exist:

```text
10:42:01  RECORDING_STARTED
10:42:02  SPEECH_DETECTED
10:42:04  SPEECH_ENDED
10:42:04  SILENCE_TIMER_STARTED
10:42:04  ABOVE_THRESHOLD_TICK
10:42:04  SPEECH_STREAK = 1
10:42:05  SPEECH_STREAK = 2
10:42:05  SPEECH_STREAK = 3
10:42:06  SILENCE_TIMER_COMPLETED
10:42:06  SPEECH_END_COMMITTED
10:42:06  RECORDING_STOPPED
10:42:06  AUDIO_UPLOAD_STARTED
10:42:07  TRANSCRIPTION_STARTED
10:42:09  TRANSCRIPTION_COMPLETED
10:42:09  COACH_RESPONSE_STARTED
10:42:11  COACH_RESPONSE_COMPLETED
```

display them in that order.

Use the **actual event names already generated by the application**.

Do not fabricate events just to make the timeline look complete.

---

## 5. Make Problems Obvious

Highlight events or sessions that indicate problems.

Especially identify existing diagnostic information related to:

* premature termination
* failed termination
* manual termination
* silence timer resets
* above-threshold noise
* genuine speech streak logic
* `speechEndCommitted`
* recording failures
* upload failures
* transcription failures
* AI response failures
* existing `COACH_*` events
* existing `BUDDY_*` events

I should be able to look at one failed session and quickly understand:

> **What happened?**

For example:

```text
Recording started
↓
Speech detected
↓
Speech ended
↓
Silence timer started
↓
Noise interrupted silence timer
↓
Silence timer restarted
↓
Speech streak guard triggered
↓
Silence timer completed
↓
VAD stopped recording
↓
Upload succeeded
↓
Transcription succeeded
↓
Coach response succeeded
```

---

## 6. Basic Filters

Add only the filters that are useful for testing:

* Date/time range
* VAD profile
* Round Buddy / Coaching
* Automatic / Manual / Failed / Premature
* Anomalies only

Keep this simple.

---

## 7. Do NOT Overbuild

This is an internal testing/debugging tool.

Do **not** build:

* a full observability platform
* complicated reporting infrastructure
* elaborate trend analysis
* predictive anomaly detection
* AI-powered diagnostics
* unnecessary database tables
* a new analytics architecture
* dashboards for metrics that aren't already supported by reliable data

The priority is **visibility into the VAD system I already built**.

---

## 8. Future-Proof the Profile Handling

The only important architectural requirement is that the dashboard must work with the application's existing multi-profile VAD engine.

If a new VAD profile is added later, it should appear automatically if the underlying system exposes it.

Do not write frontend logic like:

```text
if profile === "on_course"
if profile === "earbuds"
if profile === "carplay"
```

Use the existing canonical profile ID/name/environment data.

---

## Implementation Order

1. Inspect the existing VAD telemetry and database.
2. Identify the existing event/session data.
3. Identify the existing VAD profile model.
4. Build the simplest possible admin UI around that existing data.
5. Add the session list.
6. Add the detailed event timeline.
7. Add basic profile filtering.
8. Highlight anomalies/failures.
9. Run the existing tests.

### Most important requirement

**Do not turn this into a giant new analytics project.**

I am currently using this dashboard to test the app and diagnose real-world VAD behavior before launch.

I want to be able to answer:

> **"What happened during that recording?"**

quickly and reliably.
