# Task: Creator-Aware Landing Page

## Objective

Implement a **web-only UX improvement** for users who have an **active creator profile**.

When an authenticated creator lands on the main Post Round web landing page, display a single wide **Creator Content** tile above the existing landing-page tiles.

The tile provides a lightweight creator summary and entry point to the existing Creator Dashboard.

This is **presentation/read-only UX work only**.

Do **not** modify:

* story generation
* story qualification
* creator-story generation
* coaching-reflection generation
* approval/request behavior
* creator permissions
* sharing/grant/revocation semantics
* entitlements
* subscription logic
* `story_candidate`
* `content_ideas` generation
* player-story generation

The existing player landing page must remain unchanged for ordinary players.

---

# 1. Creator Detection

When the authenticated user loads the landing page, determine whether they have an **active creator profile** using the existing creator-profile/API architecture.

Use the existing server/API contract wherever possible.

Do **not** create a second, client-only definition of what constitutes an active creator.

The creator condition should remain consistent with the existing Creator Dashboard access model:

* authenticated user
* active creator profile

If an existing authenticated-user/profile hook or API already exposes creator status/profile information, reuse it.

Do not hardcode creator IDs, emails, slugs, or other user-specific checks.

Do not duplicate creator-profile logic across multiple frontend components.

---

# 2. Creator Content Tile

If the authenticated user is an active creator, place a single **wide Creator Content** tile **above the existing landing-page tiles**.

The existing landing-page tiles should remain below it and otherwise unchanged.

The tile should contain the following hierarchy:

## Header

**Creator Content**

## Metrics

**Followers:** `X`

**90-day subscriptions:** `X`

The subscription number must represent the existing **rolling 90-day subscription metric**.

Do not substitute:

* lifetime subscriptions
* total historical subscriptions
* current active subscriptions
* another unrelated subscription metric

Use the existing creator/subscription data source and naming conventions.

## Dashboard action

Provide a clear, lightweight action:

**View Creator Dashboard →**

This must navigate to the **existing Creator Dashboard route**.

Do not create a second dashboard route.

---

# 3. New Story Notification

The Creator Content tile should provide a lightweight indication when the creator has new stories available.

Preferred presentation:

**`X new stories`**

For example:

**3 new stories**

If the existing API/data makes the newest story header available cheaply, also show it as secondary text:

> **3 new stories**
> *How Did That Happen?*

The landing page should **not display the story body, script, hook, or full story content**.

The tile is a notification/entry point, not another dashboard.

### Important performance constraint

If obtaining the newest story header requires loading the entire Creator Dashboard payload or making a heavy request solely for this purpose, **do not do that**.

In that situation, display the new-story count only.

The landing page should remain lightweight.

---

# 4. Creator Summary Data

Before creating a new API, inspect the existing implementation.

Determine whether the current authenticated-user/creator/dashboard APIs already expose:

* active creator status
* follower count
* rolling 90-day subscription count
* new story count
* newest/newest-unread story header

Reuse existing data whenever possible.

Do not duplicate existing API requests.

Do not load the entire Creator Dashboard just to populate this tile.

If the existing API does not expose the small amount of data required, add the **smallest possible read-only API extension**.

Conceptually, the landing page needs something equivalent to:

```text
isCreator
followerCount
rolling90DaySubscriptions
newStoryCount
latestNewStoryHeader
```

These are conceptual requirements only.

**Use the project's existing naming conventions, response structures, authentication patterns, and creator API architecture rather than blindly introducing these exact field names.**

Prefer a compact creator-summary response over returning the full Creator Dashboard payload.

---

# 5. New Story Semantics

Before implementing `newStoryCount`, inspect the existing creator dashboard/content contract and determine how "new" content can correctly be identified.

Use existing server-side semantics where available.

Look for established fields such as:

* content creation timestamps
* offered/shared timestamps
* permission/grant timestamps
* read/viewed state
* content status
* creator content records
* existing dashboard notification state

Do not invent a new notification system unless the existing architecture genuinely has no suitable mechanism.

Do not modify creator permissions or content-access rules to support this feature.

The landing page must only count/display stories the creator is already entitled to see according to the existing server-side contract.

---

# 6. Respect the Current Creator Architecture

The current Creator Dashboard architecture must remain the source of truth.

The Creator Dashboard uses the established creator content pipeline and current dashboard API contract.

In particular:

* Do not switch creator content to `player_stories`.
* Do not use `player_stories` to determine creator content.
* Do not reintroduce the old `round_buddy_messages` join.
* Do not reintroduce `rounds.input_method`.
* Do not alter the current round/scorecard contract.
* Do not modify story qualification.
* Do not modify story generation.
* Do not modify coaching-reflection generation.
* Do not modify approval/request behavior.
* Do not modify creator permissions.
* Do not modify sharing/grant/revocation semantics.
* Do not modify entitlements or subscription logic.

If the existing Creator Dashboard uses:

```text
GET /api/content/ideas?story_id=...
```

or another established creator dashboard contract, leave that contract intact.

Only add a minimal read-only creator-summary capability if genuinely necessary.

---

# 7. Important Creator Access Semantics

Preserve the existing distinction between:

* creator profile status
* content availability
* permission granted
* approval requested
* revoked access

Do **not** reinterpret these states.

For example:

* an approval request is not equivalent to permission granted
* revoked content should not be surfaced as available
* creator profile status should continue to follow the existing active-profile definition

The landing page should consume the existing server-side access model rather than recreate these rules in the browser.

---

# 8. Non-Creator Experience

For an authenticated ordinary player:

* Do not render the Creator Content tile.
* Do not alter the existing landing-page layout.
* Do not alter the existing tile order.
* Do not display creator terminology.
* Do not make unnecessary creator-specific API requests.

The existing player experience should remain unchanged.

If the existing authenticated-user response can establish that the user is not a creator, do not make an additional creator-summary request.

---

# 9. Loading and Error States

Creator detection and summary data must fail gracefully.

### During loading

Avoid briefly rendering creator UI and then removing it.

Avoid unnecessary layout flashing where practical.

Use the existing application's loading/skeleton patterns if available.

### Creator-summary failure

If creator-specific summary data temporarily fails:

* do not break the landing page
* do not display fabricated follower/subscription/story values
* preserve access to the existing landing-page functionality
* do not expose raw API errors to the user

If optional latest-story-header data fails while the rest of the summary succeeds:

* continue displaying the creator tile
* continue displaying available metrics
* continue displaying the dashboard action
* simply omit the optional story header

---

# 10. Visual Design

Match the existing Post Round web application's design system.

Reuse existing:

* card/tile components
* typography
* spacing
* border radius
* shadows
* buttons
* icons
* responsive breakpoints
* loading patterns

Do not introduce a new visual design system.

The Creator Content tile should feel like a natural extension of the existing landing page.

It should be:

* wide
* visually prominent
* compact
* immediately understandable
* clearly creator-specific

Avoid turning it into a dense analytics dashboard.

The intended information hierarchy is:

```text
Creator Content

Followers: X       90-day subscriptions: X

X new stories
Latest story header, if cheaply available

View Creator Dashboard →
```

---

# 11. Responsive Behavior

Verify the Creator Content tile on:

* desktop
* tablet
* narrow/mobile web widths

It should remain one logical tile rather than requiring separate desktop/mobile implementations.

Metrics must remain readable.

The dashboard action must remain obvious and usable on narrow screens.

Do not introduce horizontal scrolling.

---

# 12. Testing

Add or update tests covering:

## Creator detection

1. Authenticated active creator → Creator Content tile renders.
2. Authenticated non-creator → Creator Content tile does not render.
3. Inactive creator profile → Creator Content tile does not render.

## Metrics

4. Correct follower count is displayed.
5. Correct rolling 90-day subscription count is displayed.
6. No fabricated values are displayed when creator-summary data is unavailable.

## New stories

7. New-story notification appears when `newStoryCount > 0`.
8. No new-story notification appears when the count is zero.
9. Latest story header is displayed when the existing/minimal API response provides it.
10. Story body/script/full story content is never rendered on the landing page.

## Navigation

11. "View Creator Dashboard →" navigates to the existing Creator Dashboard route.

## Error handling

12. Creator-summary failure does not break the rest of the landing page.
13. Optional story-header failure does not prevent the creator tile from rendering.

## Regression

14. Existing player landing page remains unchanged for ordinary users.
15. Existing landing-page tiles remain functional.

---

# 13. Implementation Process

Before changing code, inspect and identify:

1. The authenticated landing-page component.
2. The existing authenticated-user/profile loading mechanism.
3. The existing creator-profile detection mechanism.
4. The existing Creator Dashboard route.
5. The existing creator content API contract.
6. The existing follower-count source.
7. The existing rolling 90-day subscription source.
8. The existing creator story/content source.
9. Existing semantics for determining newly available creator content.

Reuse existing shared hooks, queries, API clients, and components wherever possible.

Do not create duplicate creator-profile queries or duplicate data-fetching logic.

---

# 14. Scope Boundary

This task is **landing-page UX only**.

Do not make any changes to Creator Dashboard story-card presentation or behavior as part of this task.

Do not add story collapsing/expanding functionality.

Do not modify the Creator Dashboard UI except where absolutely necessary to expose an already-existing route or API contract.

Do not modify creator business logic.

Do not modify story-generation behavior.

Do not modify approval, permission, sharing, or entitlement behavior.

---

12. Existing player landing-page behavior remains unchanged.
