# Task: Creator-Aware Landing Page — Creator Content Tile

## Objective

Implement a **web-only UX improvement** for users who have an **active creator profile**.

When an authenticated creator lands on the main Post Round web landing page, display a single wide **Creator Content** tile above the existing landing-page tiles.

The tile is intentionally focused on **creator content and new-story awareness**.

It should **not display follower counts, subscriber counts, revenue, earnings, or subscription metrics**.

This is presentation/read-only UX work only.

Do **not** modify:

* story generation
* story qualification
* creator-story generation
* coaching-reflection generation
* approval/request behavior
* creator permissions
* sharing/grant/revocation semantics
* entitlements
* subscription logic
* creator compensation logic
* `story_candidate`
* `content_ideas` generation
* player-story generation

---

# 1. Creator Detection

When the authenticated user loads the landing page, determine whether they have an **active creator profile** using the existing creator-profile/API architecture.

Use the existing server/API contract wherever possible.

Do **not** create a second, client-only definition of what constitutes an active creator.

The creator condition should remain consistent with the existing Creator Dashboard access model:

* authenticated user
* active creator profile

If an existing authenticated-user/profile hook or API already exposes creator status/profile information, reuse it.

Do not hardcode creator IDs, emails, slugs, or other user-specific checks.

Do not duplicate creator-profile logic across multiple frontend components.

---

# 2. Creator Content Tile

If the authenticated user is an active creator, place a single **wide Creator Content** tile **above the existing landing-page tiles**.

The existing landing-page tiles should remain below it and otherwise unchanged.

The purpose of this tile is to answer one simple question:

> **"Do I have creator content waiting for me?"**

The intended presentation is approximately:

```text
Creator Content

127 followers

3 new stories
How Did That Happen?

View Creator Dashboard →
```

### Important

The exact numbers/text must come from the existing data/API architecture.

Do not hardcode the example values.

---

# 3. Followers

The tile may display the creator's **current follower count**.

The authoritative definition is:

> A follower is a user whose `profiles.favorite_creator_id` points to this creator.

Conceptually:

```text
COUNT(profiles)
WHERE favorite_creator_id = creator.id
```

Use the existing creator/profile IDs and database/API conventions.

This should represent **current followers**, not historical followers.

If a player changes their favorite creator, they should no longer count toward the previous creator.

### Important

Follower count is informational only.

Do not add follower-management functionality as part of this task.

---

# 4. New Story Notification

The primary purpose of the tile is to notify the creator about new content.

Display a lightweight notification when new stories are available.

Preferred presentation:

**`X new stories`**

For example:

> **3 new stories**

If the existing API/data makes the newest story header available cheaply, show it as secondary text:

> **3 new stories**
> *How Did That Happen?*

The story header should act as a preview/notification only.

### Do NOT display:

* story body
* script
* hook
* full generated content
* coaching reflection
* scorecard
* detailed story metadata

The landing page should remain a lightweight entry point into the Creator Dashboard.

---

# 5. New Story Data

Before creating a new API, inspect the existing creator dashboard/content architecture.

Determine whether the existing creator API already exposes enough information to determine:

* number of new stories
* newest story/header
* creator-accessible content

Reuse existing data wherever possible.

Do not load the entire Creator Dashboard payload simply to populate the landing tile.

If the newest story header requires a heavy request, **display the new-story count only**.

The landing page should remain lightweight.

---

# 6. "New Story" Semantics

Before implementing `newStoryCount`, inspect the existing creator dashboard/content contract and determine how "new" content is currently represented.

Reuse established server-side semantics wherever they exist.

Look for existing concepts such as:

* content creation timestamps
* offered/shared timestamps
* creator-accessible content
* viewed/read state
* content status
* existing notification state

Do not invent a new notification system solely for this landing-page tile unless the existing architecture genuinely has no suitable mechanism.

Do not modify creator permissions or content-access rules to support this feature.

The tile must only surface stories the creator is already entitled to see according to the existing server-side contract.

---

# 7. Current Creator Architecture

Respect the existing Post Round Creator Dashboard architecture.

The Creator Dashboard uses the current creator content pipeline and existing creator API contract.

In particular:

* Do not switch creator content to `player_stories`.
* Do not use `player_stories` to determine creator content.
* Do not reintroduce the old `round_buddy_messages` join.
* Do not reintroduce `rounds.input_method`.
* Do not alter the current round/scorecard contract.
* Do not modify story qualification.
* Do not modify story generation.
* Do not modify coaching-reflection generation.
* Do not modify approval/request behavior.
* Do not modify creator permissions.
* Do not modify sharing/grant/revocation semantics.

If the existing Creator Dashboard uses:

```text
GET /api/content/ideas?story_id=...
```

or another established creator dashboard contract, leave that contract intact.

Only add a minimal read-only creator-summary capability if genuinely necessary for this tile.

---

# 8. Explicit Scope Exclusion: Subscription / Compensation Data

**Do not expose subscription or compensation information on the creator landing page.**

Specifically, do NOT add:

* subscription counts
* 90-day subscription counts
* subscriber counts
* subscription revenue
* creator earnings
* commission amounts
* compensation metrics
* subscription history

These metrics will be exposed through **administrator-only functionality** separately.

Do not create or modify creator-facing subscription/compensation APIs as part of this task.

Do not use subscription data to populate the Creator Content tile.

If you discover existing subscription-related data while inspecting the codebase, leave that functionality unchanged.

---

# 9. Dashboard Action

Provide a clear, lightweight action:

**View Creator Dashboard →**

This must navigate to the **existing Creator Dashboard route**.

Do not create a second dashboard route.

The landing tile should be an entry point, not a replacement for the dashboard.

---

# 10. Non-Creator Experience

For an authenticated ordinary player:

* Do not render the Creator Content tile.
* Do not alter the existing landing-page layout.
* Do not alter the existing tile order.
* Do not display creator terminology.
* Do not make unnecessary creator-specific API requests.

The existing player landing page should remain unchanged.

---

# 11. Loading and Error States

Creator detection and creator-summary data must fail gracefully.

### During loading

Avoid briefly rendering creator UI and then removing it.

Avoid unnecessary layout flashing where practical.

Use the existing application's loading/skeleton patterns if available.

### Creator-summary failure

If creator-specific summary data temporarily fails:

* do not break the landing page
* do not display fabricated follower/story values
* preserve access to the existing landing-page functionality
* do not expose raw API errors to the user

If optional newest-story-header data fails while the count succeeds:

* continue displaying the Creator Content tile
* continue displaying the follower count if available
* continue displaying the new-story count
* continue displaying the dashboard action
* simply omit the optional story header
