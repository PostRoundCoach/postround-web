We now have two qualified Stories successfully reaching the Creator Dashboard. The remaining broken piece is the **Generate Content** workflow.

Please inspect the existing implementation end-to-end and wire the Creator Dashboard so the intended Story workflow works without breaking the existing Story qualification, persistence, player approval UI, or handicap functionality.

## Existing intended workflow

The intended workflow is:

1. A qualifying Story is created from a player's round.
2. The qualified Story appears in the Creator Dashboard.
3. The creator clicks **Generate Content**.
4. The system generates the creator-facing content from the Story/context.
5. The creator can review the generated content.
6. The creator clicks **Request Approval** / equivalent action.
7. The player receives the approval request in the Post Round app.
8. The player approves the Story for creator use.
9. The corresponding `story_permissions` record changes to `approved`.
10. Once approved, the Story/content becomes available to the creator for use/publishing.
11. The creator should NOT be able to publish/use the Story before player approval.

### Important

Do NOT redesign this workflow.

Do NOT bypass player approval.

Do NOT automatically change `story_permissions` to `approved` when the creator generates content.

Generation and approval are two separate states/actions.

The creator may generate content, but the player must explicitly approve it before the creator can use/publish it.

# Task 3 — Separate generation from permission approval

This distinction is critical.

Generation means:

> "The creator has created a draft of content from this Story."

Approval means:

> "The player has explicitly authorized the creator to use this Story/content."

Generating content must NOT automatically approve anything.

The `story_permissions` status should remain whatever its current pending/requested state is until the player approves it.

Use the existing `story_permissions` workflow if possible.

Do not introduce a second approval system.

---

# Task 4 — Creator approval request

After successful content generation, provide the creator with an action to request approval from the player.

Use the existing permission/request infrastructure wherever possible.

The creator action should create/update the appropriate `story_permissions` record so the player can see the approval request in the Post Round app.

The workflow should be idempotent:

* clicking Request Approval multiple times should not create duplicate permission requests,
* an existing pending request should remain pending,
* an already-approved Story should remain approved,
* an already-rejected/denied Story should follow the existing application's intended behavior.

Use the existing schema/status values rather than inventing new ones unless the current implementation genuinely requires one.

Please do not blindly rewrite the feature.

First inspect the current implementation and identify why **Generate Content** is currently non-functional.

Then make the smallest coherent set of changes required to connect the existing pieces.

At the end, report:

1. Root cause of the broken Generate Content button.
2. Files changed.
3. API/server routes added or modified.
4. Database changes, if any.
5. How generated content is persisted.
6. How the approval request is created.
7. What changes when the player approves.
8. How the Creator Dashboard determines whether publishing/use is allowed.
9. Tests run and their results.

The final desired architecture is:

**Qualified Story**
→ **Creator Dashboard**
→ **Generate Content**
→ **Generated Draft**
→ **Request Player Approval**
→ **`story_permissions` pending**
→ **Player approves in Post Round**
→ **`story_permissions` approved**
→ **Creator can use/publish Story**

Keep player approval as the authoritative gate.
