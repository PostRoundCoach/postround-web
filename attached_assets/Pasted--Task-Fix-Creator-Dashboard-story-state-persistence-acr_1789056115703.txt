## Task: Fix Creator Dashboard story state persistence across logout/login

### Problem

The Creator Dashboard currently displays story actions correctly during a session, but the state is not surviving logout/login.

Observed behavior:

* Stories load correctly.
* Clicking **Dismiss** causes the story to disappear.
* Clicking **Request Approval** immediately changes the button to **Approval Requested**.
* However, after logging out and logging back in:

  * Previously dismissed stories reappear.
  * Previously requested-approval stories revert from **Approval Requested** to **Request Approval**.

This indicates that either the state is not being persisted correctly, or the dashboard is not correctly rehydrating the persisted state.

### Scope

**This task is ONLY about Creator Dashboard state persistence.**

Do not make changes to the follower/mobile approval-request experience as part of this task.

Do not redesign the Creator Dashboard.

Do not change the existing UI behavior.

Do not create a new state/approval system if the existing database architecture already supports this workflow.

### Investigation

Trace the complete lifecycle for both actions:

#### 1. Dismiss

Trace:

Creator Dashboard → dismiss handler → API/server action → database mutation → database record → dashboard reload/query → displayed state.

Determine:

* Which endpoint/server action handles Dismiss.
* Which database table and column(s) are updated.
* Which story/content identifier is stored.
* Which creator/user identifier is stored.
* Whether the production database mutation actually succeeds.
* Whether the state is stored against the correct story and creator.
* How the dashboard retrieves dismissed state when it loads.
* Whether the dashboard is using persisted state or only local React state.

#### 2. Request Approval

Trace:

Creator Dashboard → Request Approval handler → API/server action → database mutation → database record → dashboard reload/query → displayed state.

Determine:

* Which endpoint/server action handles Request Approval.
* Which database table and column(s) are updated.
* Which story/content/round identifier is stored.
* Which creator/follower identifiers are involved.
* What status is stored.
* Whether the production database mutation actually succeeds.
* How the dashboard determines that a story is already `Approval Requested` when it loads.

### Pay particular attention to identifiers

* Production Story

Make sure the persistence logic uses the correct identifier consistently.

### Required root-cause diagnosis

1. The write/mutation is failing.

3. The database state is correct but the dashboard query doesn't retrieve it.
4. The query retrieves it but the frontend doesn't hydrate/use it correctly.
5. Some combination of the above.
