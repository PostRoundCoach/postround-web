Implement the minimal fix for creator-initiated story approval requests reaching the player.

IMPORTANT: Do not redesign the approval system and do not create a second `story_permissions` row unless schema/constraint inspection proves that the existing-row model is impossible.

## Confirmed current architecture

The existing `story_permissions` row represents the creator/player/story relationship.

Current semantics:

* `permission_granted = true` means the creator relationship is active/authorized.
* `approval_requested_at` records that the creator has requested player approval for a story.
* `granted_at` represents player approval.
* `revoked_at` represents dismissal/revocation.

The existing Creator Dashboard action already operates on the existing `story_permissions` row and sets `approval_requested_at`.

Do NOT change `permission_granted` to false when the creator requests approval, because existing creator authorization and queue logic depends on `permission_granted = true`.

Do NOT create a duplicate `story_permissions` relationship row unless the schema proves that is required.

## Goal

Make the existing creator approval request visible in the existing Post Round mobile Stories experience.

The intended flow is:

Creator requests approval
→ existing `story_permissions` row gets `approval_requested_at`
→ player GET recognizes that pending-request state
→ existing Stories screen displays it
→ player approves or declines using the existing handlers.

* uses the existing decline/revoke semantics
* does not create a duplicate row

Do not invent a new status column unless the existing schema proves one is required.

The creator's existing relationship must not disappear merely because an approval request is pending.
